# 改动后清理

**简体中文** · [English](SKILL.en.md)

将清理纳入实现任务的完成条件。在本次授权改动及其直接影响范围内执行；遵循适用的项目指令和兼容承诺。正常执行有依据的清理，不为每个删除重复索取确认。不要把此技能解释为清理整个仓库、删除用户工作或修改项目规则的授权。

## 1. 确定范围与替代关系

- 先检查当前工作区状态、任务要求和相关 diff，区分本次改动与用户已有修改。
- 找到本次新增或变更的入口，以及被其替代的实现、配置、术语和文档；若任务尚未实现，先完成实现，再执行清理。
- 先搜索并复用已有能力，优先原位修改；新增模块、封装、抽象或执行路径必须解决当前的具体需要。
- 只追踪与本次改动直接相关的残留；没有可删内容时停止，不为减少行数制造重构。

## 2. 沿使用关系完成删除与收敛

- 优先用 rg 搜索旧符号、字符串名称、配置键、路由、命令和文档引用；结合调用链、导出、注册表、反射、插件发现和构建配置判断用途。
- 在新实现已接管且不再需要旧行为时，同步清理旧函数、分支、包装层、入口、开关、依赖、脚本、示例及注释。
- 同一行为优先收敛到一个实现；不要新增重复实现、注释掉的旧代码、备用副本或仅为假设需求存在的抽象。
- 只为明确兼容承诺、实际调用方或尚未完成的迁移保留兼容层、旧路径和回退逻辑，并记录具体依据。保留仍有用途的容错、校验和边界处理。
- 不以“可能以后有用”保留冗余，也不以“仓库内没有引用”判定公开 SDK/API、外部命令、部署配置、持久化格式或旧数据读取逻辑可以删除。
- 不删除历史数据库迁移、仍需执行的升级路径或有效历史记录。遇到影响外部用户或数据兼容性的未决问题，先完成可确定的清理，再说明待确认点。
- 不清除、覆盖或回退无关的用户修改和文件；不使用全局清扫、硬重置等方式代替逐项清理。

## 3. 原位维护文档

- 更新现有权威文档、导航、链接、配置示例和命令；删除已经失效的指导，避免新旧方案同时作为当前说明。
- 对仅部分失效的文档保留有效内容；尊重明确维护的版本文档、变更历史与归档。
- 项目已有对应语言版本时同步修改；不要因本技能扩大翻译范围。
- 除非用户明确要求或项目流程规定，不新增完成报告、清理报告、改造总结、重复指南或一次性说明文件。

## 4. 控制测试增量

- 新增测试前先检查现有覆盖，明确新用例能发现哪一种尚未覆盖的具体回归。优先复用、更新或适当参数化现有测试；已有覆盖足够时允许不增加用例，不为凑用例数或单纯提高覆盖率数字新增测试。
- 只为尚未覆盖的行为变化、缺陷回归、实际边界或故障风险，以及明确的项目验收要求增加必要测试。可逆、低影响且不改变行为的文案、格式、注释等改动，默认运行适用的现有检查，不新增测试。
- 不机械地为每个函数、分支或文件配测试。避免仅验证私有名称、源码字符串、行数、内部调用顺序或 mock 自身的测试，除非这些正是明确的外部契约。
- 断言应验证可观察行为，预期值应来自需求、已知案例或独立依据；不要复制被测实现生成预期结果，或增加只会随实现一起出错的测试。
- 在本次改动范围内，合并或删除确认重复、过时或没有独立断言价值的测试；先确认剩余用例仍能发现原本要防止的回归，并保留清晰的失败定位。输入相似、代码相似、断言相似或删后测试全绿，本身都不足以证明重复。
- 保留能验证不同边界、权限、并发条件、集成连接或故障模式的有效覆盖，尤其是历史缺陷和数据正确性测试。不要为了减少数量删除仍有价值的用例，也不得通过删测试或削弱断言掩盖回归。
- 遵循项目明确的测试门槛；在交付中简述必要的测试新增、合并或删除依据，不另建测试报告，不为无改动编造测试工作。

## 5. 验证并完成交付

- 再次搜索被替代的符号、配置和术语，逐项核对剩余命中，区分有效兼容和历史引用。
- 按项目约定运行与改动相关的构建、类型或静态检查，以及有意义的行为测试；涉及共享入口时覆盖受影响的调用方。
- 验证文档链接、入口注册与依赖声明的一致性。证据充分后停止扩展验证；只有具体剩余风险或项目必需门槛才触发追加检查。
- 检查最终 diff，确认没有遗漏清理、无关变更或意外删除。尊重原任务的提交、发布和授权范围。
- 在正常交付回复中简述删除或合并项、必要保留项及理由、验证结果和实际阻塞；不要另建报告文件，也不要虚构删除项或测试结果。
