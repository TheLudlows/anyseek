## “轻量提交成功即可搜索”的约束

成功前只发布有界的可查尾部，复用现有 tail；同时保证全文、向量/元数据活动身份、更新删除、向量后补和过滤一致。不能只让全文消费者追平便宣称完整可见；也不能把完整 index drain、全量重建、全局 DF 维护或每条 native 刷新直接加入新的成功边界。维护重活继续后台执行，明确准入/Busy；物理批处理若改变，须保留逐项已成功前缀、原 ID 回执以及 unknown/durable_pending/fence 恢复，不能另建提交权威。跨段评分和真实并发读写仍须另行验收。本任务没有实现立即可搜。

## 失败与未完成项

初始 overlay 轮次 1 在 HTTP 200 中遇到逐项 Busy，驱动停止；补齐原批重试后另起一套。轮次 2 的 before/1k/batch16/r1 在补向量 seq=2108 返回 durable_pending，12 项未尝试；紧接着共享磁盘出现 ENOSPC，清理本任务可再生成文件后仍被填满。**没有精确 syscall 错误证据，不将其断言为引擎缺陷或 #191 修复收益。** 两套全部已产生原始样本单独保留，不汇入 tmpfs 比较，也不标为噪声。

失败数据库复制到 tmpfs、同 before 二进制重开后，提交/两索引均为 2108，durable_pending 回执存在；1,104 个先前回执原样重放。原请求补完 12 项后水位 2120；720 条全文、400 条向量及全部 720 条记录检查通过，见归档 `recovery.json`。这是一次真实运行失败后的进程重开恢复，不是断电认证。数据库自身不提交。

真实持久盘完整对照被环境阻塞；S3、Windows、断电、长期 GC、较大正文/高维向量、并发查询、饱和队列吞吐、allocator live/lease 峰值未测。5k 只是 standard_10k 内的负载点，不是 100k 档容量承诺。后续顺序：**独占磁盘补测 → 同步逐项提交/flush 与分配归因 → 切段锁内工作 → 受这些边界约束的轻量可见发布**。
