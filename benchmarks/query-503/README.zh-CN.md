# 并发查询的发布封锁

**简体中文** · [English](README.md)

基线为 `5976daa1efb932043503298fce941a5dec03dc05`，任务开始时的最新 master，包含 #198。检查时没有重复的开放 PR。这是隔离的本地存储实验，与 #162 的容量调查分开。

## 成因与改动

正常同步批量发布在持久变更和两个索引消费者发布期间封锁输出，写入方在区间内持 partition mutex。查询评分本已在捕获与重验时获取该 mutex，但此前 HTTP handler 的初始 `output_permit`、响应构建、头部中间件及正文帧检查遇到封锁就拒绝。普通并发写入因而可产生 `503 recovery_required`，若发布在响应头交付后开始，则可能出现正文传输错误。

查询传输许可现会在既有 partition mutex 下等待发布，再执行**原有**封锁和修订检查。头部和正文交付也使用该等待。编码在锁外，同步交接在等待网络 I/O 前释放所有 guard。待发正文持有响应字节。取消会中止其独立轮询的发布等待任务。等待任务继承请求预算和关闭活动，其完成不能替代实际帧交付检查。保存的许可使用弱 partition owner，未轮询的响应不能跨重开保留旧 owner。内部调用和其他端点仍快速拒绝。WAL、索引、写入所有权和一致性屏障均保留。

[独立审查](REVIEW.zh-CN.md) 在初始候选发现无界的发布等待。最终版将头部等待纳入原请求期限，所有正文等待及重试复用该期限，晚首次轮询不会得到新预算。发布等待超时后丢弃未发送字节并返回 TimedOut，正常未消费响应仍遵循原传输 owner 的额度及生命周期。生产请求预算仍为 30 秒。

保留了负载探针的每份 HTTP 错误正文。测得的所有 503 都是 `{"code":"recovery_required","message":"RecoveryRequired"}`，没有测得 429、存储错误、未知结果或连接错误。最终矩阵的写入回执、索引文档终值和最终健康检查均通过。确定性暂停发布测试覆盖旧的快速拒绝和新的等待，消费者故障测试仍覆盖拒绝与重放恢复。基线的 503 没有逐请求内部轨迹来区分捕获、响应构建和头部交付，三个位置共用错误码，不据此推断各位置的占比。

## 复现与检查

分别构建精确基线与候选的 release 二进制，并各自复制到不可变路径。不要边编译边测。`--seed` 接收基线的 `seed-1000` 目录及同级 `seed-1000.json`，核对哈希和操作 ID epoch。输出目录不得存在。

```bash
python benchmarks/query-503/measure.py --binary /absolute/baseline --out /absolute/seed-run
python benchmarks/query-503/measure.py --binary /absolute/candidate \
  --out /absolute/candidate-run --seed /absolute/seed-run/seed-1000 \
  --endpoint batch --mode lexical
# Add --phased to synchronize every batch with eight reader requests.
python benchmarks/query-503/summarize.py /absolute/evidence --prefix deadline-paired
```

汇总器要求完整的 12 进程矩阵，命名为 `PREFIX-REP-VERSION-ENDPOINT-MODE`。从原始正文重算延迟与错误计数，检查逐项回执、最终水位、共用种子和二进制指纹。须打开断言，不静默省略失败。

基线二进制 SHA256 为 `114e91fc77f883c74b94f9a064e0a6cefe4d6b56cca71f03f9f20e3abc9a6093`。候选为 `50a08e5825c926f9910d17ecda38e2e741d41a69e877719c23e2aa2a83b9c593`。种子清单摘要为 `6f51b24898946f8cf86fc5f6ec337732e2efb69e7feab61174af0af614b5a82d`。

早期 `before-*` 与配对矩阵分开。`before-ingest-lexical` 因异步索引追平前就检查计数，触发**运行器**断言（608 indexed、lexical_seq 1608、committed_seq 1640）。保留原始失败及数据。修正后计时窗口结束再等两个消费者，不改写任何测量或失败。

本实验未验证真实 S3 或物理盘性能、较大语料容量、长期饱和、Windows 行为或更新删除性能。其他 HTTP 读端点仍快速拒绝，未纳入查询修复。

## 正确性与保留的失败

60 个相关 release/fault-injection 测试通过，含 2 个新输出等待、6 个提交批次、8 个独立查询、8 个写入、3 个发布/checkpoint 恢复和全部 33 个服务测试。服务测试含实际路由的正文/头部等待及取消、新的三场景共用期限、持久化错误正文拒绝、额度保留、集合代次及关闭。完整仓库/CI 套件未运行。

首个候选通过固定请求数 HTTP 负载，但未轮询正文仍持有在队列等待 mutex 的任务。专门背压测试在 15 秒超时。该实现弃用。最终正文等待任务独立运行，不需再次轮询即可释放 mutex，正文丢弃时中止，保留关闭活动直至清理。同一回归现通过，并验证旧正文未轮询时写入方仍完成。`first-paired-*`、所用工具、首候选二进制指纹及超时日志单独保存，不纳入最终矩阵。

`evidence.tar.gz` 包含原始请求响应正文、各进程汇总及日志、重算矩阵、环境与验证元数据、所用工具、源码差异及 SHA256 清单。数据库和二进制保留在任务环境 `/workspace/query503-evidence`，未打包到仓库。早期 ingest 驱动失败及弃用候选的超时数据库也在该目录。

经过审查的 `bba809f` 候选保留在 `paired-*` / `phased-*`，与最终 `deadline-paired-*` / `deadline-phased-*` 分开。原报告及二进制指纹已归档。独立审查发现、跟进、范围限制和超时测试结果见 [REVIEW.md](REVIEW.zh-CN.md)。
