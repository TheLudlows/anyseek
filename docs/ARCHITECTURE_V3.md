## §1 概述与定位

SeekPower v3 是一个**对象存储原生的多租户混合搜索引擎**，专为生产环境大规模部署设计。

**核心能力**：
- 🏢 **多租户隔离**：目录级物理隔离，支持无限租户
- 🔍 **混合检索**：聚类向量搜索 + 自研倒排全文检索 + RRF 融合
- 🚀 **实时索引**：写入后毫秒级可查，无需预创建 schema
- 💾 **成本优化**：基于磁盘存储，支持数十亿向量
- 🔒 **高可用**：对象存储原生，天然支持多副本和灾难恢复

## §2 核心设计决策

### 2.1 设计原则

| 原则 | 说明 |
|------|------|
| **对象存储优先** | 所有数据持久化到对象存储，引擎无状态 |
| **目录级隔离** | 每个租户独立前缀，天然多租户 |
| **无 MemTable** | 写入直接到对象存储 WAL，无内存缓冲 |
| **实时索引** | 写入 WAL 后立即可查，后台异步构建索引 |
| **Schema-Free** | 自动推断字段类型，无需预定义 |
| **成本敏感** | 对象存储为主，内存/SSD 缓存为辅 |
| **多级缓存** | L1 内存 → L2 磁盘 → L3 对象存储 |
| **一致性保证** | WAL + 版本化 manifest + CAS，ACID 语义 |

### 2.2 技术选型

| 组件 | 技术方案 | 理由 |
|------|----------|------|
| 向量索引 | 聚类索引（SPFresh 风格） | 高精度召回，磁盘原生，内存可控 |
| 全文检索 | 自研倒排索引 | 与对象存储深度集成，BM25F 支持 |
| 分词器 | Tantivy Tokenizer | 成熟方案，多语言支持 |
| 存储后端 | 对象存储 Trait | 支持 S3/FS/内存，云原生 |
| 写入路径 | 直接 WAL 到对象存储 | 无 MemTable，立即持久化，立即可查 |
| 后台索引 | 异步索引器 | 从 WAL 读取并构建 SST |
| 多租户 | 目录隔离 | 物理隔离，策略简单，天然支持 |
| 缓存系统 | L1 内存 + L2 磁盘 + L3 对象存储 | 热数据快，冷数据成本低 |
| Doc ID 分配 | CAS 序列分配器 | 基于对象存储的原子计数器 |
| 距离度量 | 余弦 / 欧氏 / 点积 | 三种都支持，灵活配置 |
| 向量维度 | 固定维度 | 简化存储和查询逻辑 |

### 3.2 数据流

**写入流程**（同步持久化，立即可查）：

```
Client → API → TenantManager → IndexManager → 分配 doc_id（CAS）
                                                       ↓
                                          WAL（对象存储，同步追加）
                                                       ↓
                                          返回 doc_id（数据已持久化）
                                                       ↓
                                  后台索引器（异步）：读 WAL → 排序 → 构建 SST → 更新 Manifest → 截断 WAL
```

**查询流程**：

```
Client → API → TenantManager → SearchManager
                                        ↓
                    ┌───────────────────┴───────────────────┐
                    ↓                                       ↓
            Cluster Search                       Inverted Search
                    ↓                                       ↓
              Top-K Vectors                         Top-K Docs
                    └───────────────────┬───────────────────┘
                                        ↓
                                 RRF Fusion → Top-K Results → Fetch Docs (async) → Response
```

## §4 多租户隔离设计

### 4.1 隔离策略：目录级物理隔离

每个租户拥有独立的对象存储前缀，实现物理隔离。详细的索引级目录结构见 [§9.2 存储布局](#92-存储布局)。

```
object-store://bucket/
├── tenant-{tenant_id}/
│   ├── registry.json          # 租户元数据
│   ├── indexes/
│   │   └── index-{name}/      # 见 §9.2
│   └── quota/                 # 配额信息
└── tenant-{tenant_id}/
    └── ...
```

路径规则（`TenantRouter`）：
- 租户前缀：`tenant-{tenant_id}`
- 索引前缀：`tenant-{tenant_id}/indexes/{index_name}`

### 4.2 租户元数据

**TenantRegistry** 包含：租户 ID、名称、状态、创建时间、配额限制（最大索引数、最大文档数、最大存储容量、QPS 限制）、索引列表。从对象存储加载并缓存。

### 4.3 资源配额

`QuotaManager` 在每次操作时检查：

| 操作 | 检查点 |
|------|--------|
| 创建索引 | `max_indexes` |
| 索引文档 | `max_documents`, `max_storage_bytes` |
| 搜索查询 | QPS 限制（令牌桶） |

## §6 Schema-Free 设计

### 6.1 自动 Schema 推断

无需预定义 schema，引擎自动推断字段类型。

**FieldType 类型**：
- Text：文本，分词索引
- Keyword：关键词，精确匹配
- U64：64 位无符号整数（非负整数）
- I64：64 位有符号整数
- F32：32 位浮点数
- F64：64 位浮点数
- Bool：布尔值
- Timestamp：时间戳
- Vector(u32)：向量（固定维度，F32 数组自动推断）
- Json：JSON 对象（不索引）

**FieldMetadata** 包含字段名称、类型、是否索引、是否存储、首次出现时间、样本数量。

### 6.2 Schema 推断策略

| 字段值 | 推断类型 | 策略 |
|--------|----------|------|
| String < 100 字符 | Keyword | 短文本精确匹配 |
| String ≥ 100 字符 | Text | 长文本分词索引 |
| F32 数组（非空，同类型） | Vector(dim=长度) | 向量索引（固定维度） |
| F32 值 | F32 | 32 位浮点数 |
| F64 值 | F64 | 64 位浮点数 |
| Integer（非负） | U64 | 无符号整数 |
| Integer（负数） | I64 | 有符号整数 |
| Boolean | Bool | 布尔索引 |
| 空数组 / 混合类型数组 | Json | 不索引，仅存储 |
| Object | Json | 不索引，仅存储 |
| Null | Keyword | 精确匹配 |

**类型收敛规则**（字段类型冲突时升级为更通用类型）：
- Keyword + Text → Text
- U64 + I64 → I64
- I64 + F32 → F64
- F32 + F64 → F64
- I64 + F64 → F64
- U64 + F32 → F64
- U64 + F64 → F64
- 其他冲突 → Json

**向量维度约束**：首次推断后维度固定，后续写入不一致维度报错。

### 6.3 Schema 存储与演化

Schema 随 manifest 持久化，包含版本、字段映射、创建/更新时间。推断逻辑：对文档中每个字段，已存在则更新样本计数并检查类型收敛，不存在则推断类型创建新字段，最后更新修改时间。

## §7 聚类向量索引

### 7.1 SPFresh 风格聚类基础结构

基于 K-Means 聚类的向量索引，受 SPFresh 启发：

```
                    ┌─────────────────┐
                    │  Query Vector q │
                    └────────┬────────┘
                             │
                    计算到各聚类中心的距离
                             │
           ┌─────────────────┼─────────────────┐
           ↓                 ↓                 ↓
    ┌──────────┐      ┌──────────┐      ┌──────────┐
    │ Cluster  │      │ Cluster  │      │ Cluster  │
    │   Top-K  │      │  Others  │      │  Others  │
    └────┬─────┘      └────┬─────┘      └────┬─────┘
         │                 │                 │
    在选定的 nprobe 个聚类中搜索                │
         │                 │                 │
         └─────────────────┴─────────────────┘
                             │
                        合并结果 → Top-K
```

### 7.2 磁盘布局设计

#### 聚类元数据存储

```
segments/seg_{id}/clusters.meta
┌─────────────────────────────────────────────┐
│ Header:                                      │
│   - format_version: u32                      │
│   - num_clusters: u32                        │
│   - dimension: u32                           │
│   - distance_metric: DistanceMetric          │
│   - max_vectors_per_cluster: u64             │
├─────────────────────────────────────────────┤
│ Cluster Centers:                             │
│   For each cluster:                          │
│     - cluster_id: u32                        │
│     - center: [f32; dimension]               │
│     - num_vectors: u64                       │
│     - vector_offset: u64                     │
│     - size_bytes: u64                        │
├─────────────────────────────────────────────┤
│ Cluster Statistics:                          │
│   For each cluster:                          │
│     - avg_radius: f32                        │
│     - max_radius: f32                        │
│     - variance: f32                          │
└─────────────────────────────────────────────┘
```

#### 向量数据存储（按聚类分区，列式 SIMD 对齐）

```
segments/seg_{id}/vectors.bin
┌─────────────────────────────────────────────┐
│ Header:                                      │
│   - format_version: u32                      │
│   - dimension: u32                           │
│   - num_vectors: u64                         │
│   - data_type: DataType (F32)                │
│   - num_clusters: u32                        │
├─────────────────────────────────────────────┤
│ Cluster 0 Vectors (column-major for SIMD):   │
│   vec_0[0], vec_1[0], ..., vec_n[0],         │
│   vec_0[1], vec_1[1], ..., vec_n[1],         │
│   ...                                         │
│   (基于 SIMD 对齐，支持 range read)          │
├─────────────────────────────────────────────┤
│ Cluster 1..N Vectors...                      │
└─────────────────────────────────────────────┘
```

#### 文档 ID 映射

```
segments/seg_{id}/doc_ids.bin
┌─────────────────────────────────────────────┐
│ Header:                                      │
│   - format_version: u32                      │
│   - num_vectors: u64                         │
├─────────────────────────────────────────────┤
│ Doc ID Mapping (cluster_id, local_id → doc_id): │
│   For each cluster:                          │
│     - cluster_id: u32                        │
│     - num_vectors: u64                       │
│     - doc_ids: [u64; num_vectors]            │
│       (delta varint encoding)                │
└─────────────────────────────────────────────┘
```

### 7.3 距离度量

- **Cosine**：1 - 余弦相似度（归一化后使用）
- **Euclidean**：L2 距离平方
- **Dot**：1 - 点积（适用于归一化向量的相似度搜索）

### 7.4 查询流程

```
Query Vector q
  ↓
1. 计算到所有聚类中心的距离
2. 选择距离最近的 nprobe 个聚类
3. 并行搜索选定的聚类（从 vectors.bin 读取，计算精确距离）
4. 合并并排序结果，返回 Top-K
```

`ClusterIndex` 持有对象存储引用、聚类元数据、维度、距离度量、`nprobe` 参数。`search_cluster` 从磁盘加载指定聚类的向量和文档 ID，计算距离并返回排序后的 Top-N。

### 7.5 聚类缓存策略

- **聚类中心缓存**：所有聚类中心常驻内存
- **热度统计**：跟踪每个聚类的访问频率
- **按需加载**：向量数据按需加载（LRU）
- **预取**：搜索时预取邻近聚类

`ClusterCache` 持有聚类中心（常驻内存）、热聚类向量缓存（LRU）、访问频率统计。

### 7.6 聚类构建

`ClusterBuilder` 使用 Mini-Batch K-Means：初始化聚类中心 → 迭代（分配到最近聚类，更新中心）→ 返回聚类元数据（数量、维度、中心点、距离度量）。

## §8 自研倒排索引

### 8.1 段内结构

```
segments/seg_{id}/lex.bin
┌─────────────────────────────────────────────┐
│ Header:                                      │
│   - format_version: u32                      │
│   - num_fields: u32                          │
│   - doc_count: u64                           │
├─────────────────────────────────────────────┤
│ Field Metadata Table:                        │
│   For each field:                            │
│     - field_name_len: u16                    │
│     - field_name: [u8]                       │
│     - fst_offset: u64                        │
│     - postings_offset: u64                   │
│     - field_statistics_offset: u64           │
├─────────────────────────────────────────────┤
│ Field Statistics (per field):                │
│   - sum_total_tf: u64                        │
│   - sum_doc_len: u64                         │
│   - doc_count: u64                           │
│   - avg_doc_len: f64                         │
├─────────────────────────────────────────────┤
│ Term Dictionary (FST):                       │
│   term → (postings_offset, term_freq, df)   │
├─────────────────────────────────────────────┤
│ Postings Lists:                              │
│   For each term:                             │
│     - doc_count: u32                         │
│     - doc_id_list: [delta varint]           │
│     - term_freq_list: [varint]              │
│     - positions_list (optional):             │
│       For each doc:                          │
│         - num_positions: u16                 │
│         - positions: [delta varint]         │
└─────────────────────────────────────────────┘
```

### 8.2 分词器集成

复用 Tantivy Tokenizer：`Tokenizer` Trait 提供 `tokenize` 方法；`JiebaTokenizer` 封装 Tantivy 的中文分词器，返回 Token 列表。

### 8.3 BM25F 评分

`Bm25fScorer` 持有参数 `k1`、`b` 和字段权重映射。`score` 计算：
1. 获取字段权重
2. 计算 IDF：`ln((total_docs - df + 0.5) / (df + 0.5) + 1.0)`
3. 计算 TF 归一化：`tf * (k1 + 1) / (tf + k1 * (1 - b + b * doc_len / avg_doc_len))`
4. 返回 `field_weight * idf * tf_norm`

### 8.4 查询执行

`LexicalIndex` 持有对象存储引用、段列表、删除集。`search` 按查询类型分发：
- **Term**：单个词项搜索
- **Phrase**：短语搜索（支持 slop）
- **Boolean**：布尔组合（must/should/must_not）

`term_search`：并行搜索所有段 → 合并结果并过滤删除集 → 返回 Top-K。

## §9 文档存储设计

### 9.1 WAL-First 架构

文档存储采用 **WAL-First + 异步索引** 架构，核心创新：**无 MemTable，直接写入对象存储 WAL**。

```
┌─────────────┐    ┌────────────────────┐    ┌─────────────────┐
│   文档写入   │ → │  WAL (对象存储)     │ → │  立即返回 doc_id │
│  (分配doc_id) │    │  同步追加写入       │    │  (数据已持久化)  │
└─────────────┘    └────────────────────┘    └────────┬────────┘
                                                           │
                                      查询可从 WAL 读取 (O(log n))
                                                           │
                            后台索引器（异步）：读 WAL → 排序构建 SST → 更新 Manifest → 截断 WAL
                                                           │
                      ┌────────────────────────────┐        │
                      │   SST 文件 (对象存储)      │◄───────┘
                      │   按序存储，二分查找        │
                      └────────────────────────────┘
```

**关键特性**：
- **无 MemTable**：不消耗大量内存缓冲文档
- **立即持久化**：WAL 写入对象存储后立即可查
- **后台索引**：异步构建 SST，不影响写入延迟
- **反压机制**：WAL 超过阈值时返回 429，防止无限增长
- **无状态计算节点**：所有数据在对象存储，可水平扩展

**对比传统 LSM**：

| 组件 | 传统 LSM | Turbopuffer 风格 |
|------|----------|------------------|
| MemTable | 内存缓冲 (64MB) | ❌ 无 |
| WAL | 本地磁盘 | ✅ 对象存储 |
| L0 段 | 未排序 | ❌ 无（WAL 充当未排序层） |
| L1+ 段 | 多层分级 | ✅ 单层 SST |
| 索引构建 | Flush 触发 | 后台异步索引器 |

### 9.2 存储布局

```
{index_prefix} = "tenant-{tenant_id}/indexes/{index_name}"

├── manifest.json              # Index manifest（SST 列表、版本）

├── wal/                       # WAL 段（对象存储）

│   ├── {seq}.idx             # WAL 索引（doc_id → offset，O(log n) 查找）
```

### 9.3 Doc ID 分配（CAS 序列）

**无 MemTable 时如何分配 doc_id？** 使用 **CAS (Compare-And-Swap)** 在对象存储上维护原子计数器（路径 `{index_prefix}/sequence`，格式 `u64`）：

```rust
pub async fn allocate_doc_id(&self) -> Result<u64> {
    loop {
        // 1. 读取当前序列号
        let current = self.read_sequence().await?;
        // 2. 递增
        let next = current + 1;
        // 3. CAS 更新（put_if_match）
        if self.store.put_if_match("sequence", next.to_bytes(), current.etag).await? {
            return Ok(next);
        }
        // 4. 冲突重试
    }
}
```

**优化**：批量分配（一次 CAS 获取 N 个 doc_id，减少竞争）+ 本地缓存（维护本地分配窗口，减少 CAS 调用）。

### 9.4 文档格式

**Document** 包含：
- doc_id：文档 ID（全局唯一，递增）
- fields：字段映射
  - String：文本
  - Integer(i64)：整数
  - F32(f32)：32 位浮点数
  - F64(f64)：64 位浮点数
  - Boolean(bool)：布尔值
  - Null：空值
  - Array(Vec<DocumentValue>)：数组（F32 数组可推断为 Vector）
  - Object(HashMap<...>)：嵌套对象
- timestamp：时间戳（Unix 毫秒）

### 9.5 查询流程（多级缓存）

文档查询遵循 **L1 → L2 → L3 → WAL** 的缓存层次：

```
查询 doc_id = N
  ↓
1. 检查删除集（持久化）
2. L1 缓存（内存 LRU）    命中？→ 返回（~8ms）
3. L2 缓存（磁盘/SSD LRU） 命中？→ 返回（~50ms），回填 L1
4. L3 对象存储（SST）     命中？→ 返回（~200ms），回填 L2 和 L1
5. WAL（对象存储，未索引）  命中？→ 返回（~300ms），回填缓存
6. NotFound
```

**缓存优化**：预热（搜索时预取相邻文档）、按需加载（索引只返回 doc_id，原文异步加载）、空间回收（LRU 淘汰 + TTL 过期）、布隆过滤（快速判断是否需要查 SST）。

### 9.6 后台索引器

**职责**：从 WAL 读取数据，构建 SST，更新 manifest。

```
1. 扫描 WAL 段（读取未处理的 seq 范围，获取 ADD/DELETE 记录）
2. 构建内存缓冲（应用删除集，按 doc_id 排序）
3. 构建 SST（写入二进制格式，上传到对象存储）
4. 更新 Manifest（CAS：添加段元数据，递增版本号）
5. 截断 WAL（删除已处理的 WAL 段，更新序列状态）
```

**触发条件**：WAL 大小超过阈值（默认 2GB）/ 时间间隔（默认 5 分钟）/ 手动触发。

**反压**：WAL 超过 2GB → 返回 HTTP 429，客户端等待/重试。

**运行模式**：独立进程或后台任务，可水平扩展（多消费者并行处理），失败重试 + 检查点恢复。

### 9.7 删除机制

- **软删除**：写入 DELETE 记录到 WAL
- **持久化**：删除集定期持久化到 `delete_set.json`
- **查询过滤**：查询时检查删除集
- **物理清理**：索引器构建 SST 时跳过已删除文档

### 9.8 分块策略

- **阈值**：4MB（可配置）
- **触发条件**：文档 JSON 字符串长度 > 4MB
- **分块方式**：按字段数量分块（默认 100 字段/块）
- **自动合并**：读取时自动合并所有分块

## §10 实时索引机制

### 10.1 实时可查性

**写入后如何立即查询？**

1. **读取 WAL**：查询时从对象存储读取未索引的 WAL 段
2. **缓存 WAL 索引**：维护 WAL 索引在 L1/L2 缓存
3. **背景查询**：并行查询 WAL 和 SST，合并结果

```
┌─────────────┐
│ 查询 doc_id │
└──────┬──────┘
       ↓
并行查询：L1/L2 缓存 + WAL 段（对象存储）+ SST 文件（对象存储）
       ↓
   合并结果（取最新）→ 返回文档
```

**关键差异**：无内存索引结构；WAL 写入后直接可查；WAL 在 S3/FS 而非本地磁盘。

### 10.2 WAL 格式（增强）

```
wal/{seq}.wal
┌─────────────────────────────────────────────┐
│ Header:                                      │
│   - magic: [u8; 4] = b"WLOG"                │
│   - version: u32                             │
│   - sequence: u64                           │
│   - checksum: u32                            │
├─────────────────────────────────────────────┤
│ Records:                                     │
│   For each record:                           │
│     - record_type: u8 (ADD/DELETE)          │
│     - doc_id: u64                            │
│     - payload_len: u32                       │
│     - payload: Document JSON                │
│     - checksum: u32                          │
├─────────────────────────────────────────────┤
│ Trailer:                                     │
│   - record_count: u64                        │
│   - end_offset: u64                          │
│   - checksum: u32                            │
└─────────────────────────────────────────────┘

wal/{seq}.idx  ← WAL 索引（可选，加速查询）
┌─────────────────────────────────────────────┐
│ [doc_id(8) + offset(8)] * n                  │
│ 支持 O(log n) 的 WAL 查找                   │
└─────────────────────────────────────────────┘
```

### 10.3 索引构建

后台索引器内部组件：

```
Indexer
├── WALConsumer（读取 WAL）
├── VectorIndexBuilder（向量索引，见 §7）
├── LexicalIndexBuilder（倒排索引，见 §8）
├── SegmentWriter（SST 写入）
└── ManifestUpdater（版本管理）
```

- **向量索引**：从 WAL 读取向量 → 批量收集（min_batch_size）→ Mini-Batch K-Means → 写 `clusters.meta` + `vectors.bin`
- **倒排索引**：从 WAL 读取文本字段 → 分词 → 构建 FST 词项字典 + Postings + 统计信息（TF, DF）→ 写 `lex.bin`

## §11 混合搜索与融合

### 11.1 RRF (Reciprocal Rank Fusion)

`RrfFusion` 持有词法权重、向量权重、RRF 常数 k（通常 60）。`fuse` 方法：
1. 累加词法搜索 RRF 分数：`weight / (k + rank)`
2. 累加向量搜索 RRF 分数：`weight / (k + rank)`
3. 按 RRF 总分排序并返回

### 11.2 元数据过滤

支持在融合前进行元数据过滤：先应用过滤条件获取 doc_id 集合 → 在过滤后的集合上执行词法和向量搜索 → 融合结果。

## §13 并发模型

### 13.1 锁策略

```
DocStore:
  ├── manifest: RwLock<IndexManifest>
  ├── schema: RwLock<Schema>
```

## §14 缓存策略

### 14.1 三级缓存架构

```
┌─────────────────────────────────────────────────────────────┐
│  L1: 内存缓存 (In-Memory LRU)                                │
│  - 速度: ~1-10ms                                             │
│  - 容量: 1GB (可配置)                                        │
│  - 策略: LRU + 访问频率                                       │
│  - 数据: 热文档、热聚类、索引元数据                           │
└────────────────────────┬────────────────────────────────────┘
                         │ miss
                         ↓
┌─────────────────────────────────────────────────────────────┐
│  L2: 磁盘/SSD 缓存 (Local Disk Cache)                        │
│  - 速度: ~10-50ms                                            │
│  - 容量: 100GB (可配置)                                      │
│  - 策略: LRU + TTL (默认 24h)                                │
│  - 数据: 温数据、大型向量段、倒排索引                        │
└────────────────────────┬────────────────────────────────────┘
                         │ miss
                         ↓
┌─────────────────────────────────────────────────────────────┐
│  L3: 对象存储 (S3 / FS / Memory)                             │
│  - 速度: S3 ~200-500ms, FS ~10-50ms                         │
│  - 容量: 无限                                                │
│  - 策略: 持久化存储                                          │
│  - 数据: 所有持久化数据 (WAL, SST, 文档)                     │
└─────────────────────────────────────────────────────────────┘
```

### 14.2 缓存策略表

| 数据类型 | 缓存层级 | 策略 | TTL |
|----------|----------|------|-----|
| Manifest | L1 | 版本验证，短缓存 | 1s |
| Schema | L1 | 长缓存 | 10min |
| 序列号 | L1 | CAS 原子更新，不缓存 | N/A |
| 聚类中心 | L1 | 常驻内存 | 无 |
| 聚类向量数据 | L1+L2 | LRU，预取邻近聚类 | 1h |
| 向量索引段 | L1+L2 | 按聚类热度淘汰 | 24h |
| FST 词典 | L1 | 常驻内存（通常较小） | 无 |
| 倒排列表 | L1+L2 | LRU，按查询热度 | 24h |
| 文档 (小) | L1+L2 | LRU，按访问频率 | 24h |
| 文档 (大) | L2 | 仅磁盘缓存，不进内存 | 24h |
| WAL 段 | L1+L2 | 最近活跃的 WAL 段 | 1h |
| WAL 索引 | L1 | 常驻，加速 WAL 查询 | 无 |

### 14.3 缓存实现

```rust
pub struct CacheEngine {
    /// L1: 进程内 LRU 缓存
    l1: Arc<LruCache<CacheKey, CacheValue>>,
    /// L2: 本地磁盘缓存（可选）
    l2: Option<Arc<DiskCache>>,
    /// L3: 对象存储（只读引用）
    store: Arc<dyn ObjectStore>,
}

pub enum CacheKey {
    Document(u64),
    Segment(u64),
    ClusterCenter(u32),
    VectorData { cluster_id: u32, offset: u64 },
    PostingList { field: String, term: String },
    Manifest,
    Schema,
}

impl CacheEngine {
    /// 三级缓存查找
    pub async fn get(&self, key: &CacheKey) -> Result<Option<Bytes>> {
        // 1. L1 查找
        if let Some(v) = self.l1.get(key) {
            return Ok(Some(v.clone()));
        }
        // 2. L2 查找
        if let Some(l2) = &self.l2 {
            if let Some(v) = l2.get(key).await? {
                self.l1.put(key.clone(), v.clone()); // 回填 L1
                return Ok(Some(v));
            }
        }
        // 3. L3 查找（对象存储）
        let path = key.to_path();
        let bytes = self.store.get(&path).await?;
        // 4. 回填缓存
        self.l1.put(key.clone(), bytes.clone());
        if let Some(l2) = &self.l2 {
            l2.put(key, bytes.clone()).await?;
        }
        Ok(Some(bytes))
    }

    /// 写入缓存（通常用于写操作后）
    pub async fn put(&self, key: CacheKey, bytes: Bytes) {
        self.l1.put(key.clone(), bytes.clone());
        if let Some(l2) = &self.l2 {
            let _ = l2.put(key, bytes).await;
        }
    }
}
```

### 14.4 预取与淘汰

**预取**：聚类预取（查询聚类 N 时预取 N±1）、文档预取（查询 doc_id=N 时预取 N-1..N+10）、倒排预取（查询 term 时预取相似词的倒排列表）。基于查询历史的 LRU 权重调整与时序模式识别。

**淘汰**：
- **LRU**：基于访问时间，访问频率加权（最近 5 分钟内访问提升优先级）
- **TTL**：文档 24h、向量数据 1h、WAL 段 1h（索引完成后更快淘汰）
- **空间**：L1 超容量淘汰 20% 最冷数据，L2 淘汰 10%，按索引级别优先保留热索引数据

### 14.5 缓存统计

```rust
pub struct CacheStats {
    pub l1_hits: u64,
    pub l2_hits: u64,
    pub l3_hits: u64,
    pub total_requests: u64,
    pub l1_size_bytes: u64,
    pub l2_size_bytes: u64,
}

impl CacheStats {
    pub fn hit_rate(&self) -> f64 {
        (self.l1_hits + self.l2_hits) as f64 / self.total_requests as f64
    }
    pub fn l1_hit_rate(&self) -> f64 { self.l1_hits as f64 / self.total_requests as f64 }
    pub fn l2_hit_rate(&self) -> f64 { self.l2_hits as f64 / self.total_requests as f64 }
}
```

## §15 创新设计亮点

| 亮点 | 核心点 | 优势 |
|------|--------|------|
| **无 MemTable 的 WAL-First** ⭐ | 彻底移除 MemTable，写入直达对象存储 WAL，立即可查，后台异步建索引 | 极低内存占用、写入延迟稳定、无状态可水平扩展、WAL 重放崩溃恢复 |
| **三级缓存架构** | L1 内存 + L2 磁盘 + L3 对象存储，智能预取与淘汰 | 热数据极速、冷数据低成本、自动管理 |
| **目录级多租户隔离** | 租户独立前缀 + 配额管理 | 实现简单、支持按租户迁移/备份/扩展到不同后端 |
| **Schema-Free 自动推断** | 自动推断字段类型 + 类型收敛 + 无锁演化 | 开发体验佳、适应动态数据、降低门槛 |
| **聚类向量索引 + 对象存储原生** | SPFresh 风格 K-Means，聚类中心常驻内存，向量按需加载，仅搜索 nprobe 个聚类 | 高精度召回（P99 < 100ms）、支持十亿级、内存可控 |
| **原文分离 + 按需加载** | 索引与原文分离，搜索只返回 doc_id，原文异步加载 | 索引延迟极低、支持大规模文档、存储策略灵活 |
| **多距离度量** | 余弦/欧氏/点积，固定维度 | 一套索引多场景，无需重建即可切换 |
| **复用 Tantivy 分词器** | 复用成熟分词器，多语言支持 | 成熟稳定、开发成本低 |

## §18 可靠性保证

### 18.1 ACID 语义

- **原子性**：WAL 同步写入对象存储
- **一致性**：Manifest 版本化 + Schema 约束 + CAS 更新
- **隔离性**：RwLock + MVCC（读快照）
- **持久性**：WAL 对象存储持久化

### 18.2 灾难恢复

1. **WAL 恢复**：启动时重放 WAL，重建状态
2. **Manifest 恢复**：从对象存储加载最新 manifest
3. **段恢复**：加载所有活跃段
4. **删除集恢复**：从 manifest 加载删除集
5. **检查点恢复**：索引器从检查点继续处理 WAL

### 18.3 数据一致性

- **CAS 写入**：Manifest 更新使用 If-Match
- **校验和**：所有文件带 CRC32 校验
- **版本验证**：读取时验证 manifest 版本
