## Automatic Routing of Origence Workspace (2026-11-17)

Tenant namespace validation is independent and uses `^[a-z0-9][a-z0-9_-]{0,62}$`, which supports application UUIDs. Collection names retain the lowercase-letter start rule. Catalog paths, strict SQLite reopening, service backup path validation, HTTP, SDK, and console agree on namespaces. Origence sends the tenant UUID and maps the workspace to `ws_<无连字符 UUID>` (UUID without hyphens). The host creates collections on first use, with no tenant registration, tenant keys, or mapping table. `/api/v1/live` remains public, validates `apikey` when provided, and supports startup checks before provisioning collections.

## Convergence of Catalog and Service Authentication Responsibilities (2026-11-17)

Based on the master `bb53b80`. Collections, backup ownership, and management receipts continue to use SQLite; tenant registration and tenant key issuance, persistence, revocation, and authentication are removed. User authentication and permissions are handled by Origence/Gateway; AnySeek only verifies the service credentials derived from process configuration, retaining trusted tenant namespaces.

- Catalog 7 keeps only four tables: `catalog_meta`, `catalog_collections`, `catalog_backups` and `catalog_operations`. Collection changes and management receipts commit in the same short transaction. Backup ownership, generation reclamation, historical management ID isolation and full service restore are preserved. Catalog no longer maintains a native log or stores master credential verification material.
- The data interface requires `apikey` service credentials and `X-AnySeek-Tenant`; tenants do not need to register. `/api/v1/tenants` and `/api/v1/apikey` are removed, and collection lists are unified as `GET /api/v1/index`. When querying management receipts, searches are performed by namespace if there is a tenant header, with the default used for service-level operations. Incorrect credentials, missing, or duplicate tenant headers are rejected before the body.
- The console selects only the tenant and accesses the gateway through an upstream login session. The service credential stays in the gateway or local Vite proxy. Connection fingerprints for pending operations are isolated by origin and namespace.
- S3 authority schema 3 and backup snapshot 2 retain their protocol and share `metadata.sqlite` with Catalog. Storage contracts, strict reopening of existing databases, the reduction in duplicate SQL for upload reservation and registration, and retirement rechecks after I/O are retained.
- The restore target uses its own master credential configuration. See the [storage protocol](storage.en.md) for supported formats.

## Capacity and architectural boundaries

Full logical State remains resident. Collection capacity depends on memory admission, checkpoint and journal byte budgets, and the input workload. Bounded admission and explicit buffer budgets do not hard-limit whole-process RSS or disk. The default service shares SQLite authority and a verified object cache. Multiple authorities, materialized indexes, and separate backups need total-capacity assessment.

Receipts become eligible for reclamation two days after creation, subject to the retry window, certified historical floor, generation, reader and backup protection. There is no fixed cleanup deadline. Capacity limits cannot be lifted by deleting protected receipts within the window. S3 mode requires metadata.sqlite, SQLite WAL and the owner lock file. The bucket alone cannot reconstruct authority. Initial SQLite support provides neither cross-host HA nor zero RPO if the authority volume is lost.

Very large collection sharding, automatic split/merge, cross-host HA, direct remote Directory, prefetch, and automatic scheduling are deferred until workloads justify them. PR #110 for #107 Catalog/Generation research is closed. Resume measurement only with a demonstrated workload bottleneck. No assumption of one internal watermark, replacing Operation IDs with UUIDs, or rebuilding the execution framework. Source, graph relationships, and memory policy are application concerns. Model inference, parsing/chunking, Embedding/Reflect, SQL/JOIN, a full graph language, and legacy migration are outside this scope.
